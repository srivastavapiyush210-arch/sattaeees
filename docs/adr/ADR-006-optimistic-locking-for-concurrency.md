# ADR-006: Optimistic Locking for Concurrency Control

## Status
**Accepted**

## Context
In a multi-user daily wage labor marketplace, concurrent interactions create critical race conditions:
1. **Lost Updates on Job State:** A worker attempts to mark a job `IN_PROGRESS` at the exact millisecond the customer attempts to cancel it (`CANCELLED`). Without concurrency controls, the last write silently overwrites the previous write.
2. **Double Booking / Availability Thrashing:** Multiple customers may attempt to assign or update worker assignments simultaneously.
3. **Rating Aggregation Collisions:** Multiple customers submitting reviews for the same worker concurrently could overwrite `average_rating` calculations.

## Decision
We implemented **Optimistic Locking** using JPA's `@Version` mechanism across all domain entities via `BaseAuditableEntity`:

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseAuditableEntity {
    // ...
    @Version
    @Column(name = "version", nullable = false)
    private Long version = 0L;
}
```

1. **Mechanism:** Every `UPDATE` statement generated by Hibernate appends a version check:
   ```sql
   UPDATE job_requests SET status = 'IN_PROGRESS', version = 2 
   WHERE id = 105 AND version = 1;
   ```
2. **Conflict Detection:** If another transaction modified the row in the interim, Hibernate detects 0 rows updated and throws `OptimisticLockException` (wrapped in Spring's `OptimisticLockingFailureException`).
3. **API Response:** The `GlobalExceptionHandler` maps this to HTTP 409 Conflict:
   ```json
   {
     "timestamp": "2026-09-26T18:30:00",
     "status": 409,
     "error": "Conflict",
     "message": "Resource was modified by another transaction. Please reload and try again.",
     "path": "/api/job-requests/105/status",
     "traceId": "c59e78a01123491f"
   }
   ```

## Consequences

### Positive:
- **No Database Locks:** Reads and writes never hold persistent row or table locks (`SELECT FOR UPDATE`), eliminating database deadlocks and maximizing throughput.
- **Data Integrity:** Guarantees that stale reads can never silently overwrite fresher state.
- **Fail-Fast Semantics:** Concurrency conflicts are immediately surfaced to the client for graceful UI retry or refresh.

### Negative:
- In extremely high-contention scenarios (e.g. thousands of concurrent writes to the same row per second), optimistic locking leads to frequent retries. However, Sattaees' access patterns have high read volume and low entity write contention, making optimistic locking the ideal choice.

## Alternatives Considered
- **Pessimistic Locking (`SELECT FOR UPDATE`):** Holds exclusive database row locks for the duration of the transaction. Rejected because it blocks concurrent reads, degrades database connection pool throughput, and increases deadlock risk.
- **No Locking (Last-Write-Wins):** Rejected due to risk of silent data corruption and inconsistent state transitions.
